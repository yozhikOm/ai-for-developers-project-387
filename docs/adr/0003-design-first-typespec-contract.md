# Design First: TypeSpec-контракт — единый источник правды

Приложение делается в подходе Design First: сначала фиксируется поведение
системы и API-контракт, затем фронтенд и бекенд реализуются по нему раздельно.
Контракт задаёт границу между `apps/web` и `apps/api` и описывается в TypeSpec.
OpenAPI-спецификация, клиентский SDK для фронтенда и серверные артефакты (типы,
проверка запросов, маршруты) генерируются из него одной командой.
Сгенерированное руками не правится: изменение API начинается с правки контракта.

## Considered Options

- **OpenAPI YAML вручную**: без инструментов, но многословно, и дублирование
  схем приходится держать руками.
- **Таблица эндпоинтов в спецификации**: дёшево, но контракт не машиночитаемый —
  нечего генерировать и нечем проверять запросы.
- **Code-first** (контракт выводится из кода сервера): граница определяется
  реализацией бекенда, фронтенд нельзя делать параллельно по готовому контракту.

## Consequences

- Контракт растёт вместе с вертикальными тикетами реализации: каждый тикет
  проходит слои «контракт → сервер → интерфейс → тесты».
- Спецификация описывает поведение (бизнес-правила, семантику ошибок), а формы
  запросов и ответов живут только в контракте.
