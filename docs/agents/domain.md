# Доменные документы

Как инженерные скиллы должны читать доменную документацию этого репозитория
при исследовании кодовой базы.

## Перед исследованием читай

- **`GLOSSARY.md`** в корне репозитория;
- **`docs/adr/`** — ADR-и, затрагивающие ту область, в которой собираешься
  работать.

Если этих файлов нет, **продолжай молча**: не сообщай об их отсутствии и не
предлагай создать их заранее. Скилл `/domain-modeling` (через
`/grill-with-docs` и `/improve-codebase-architecture`) создаёт их лениво — когда
термины и решения действительно проясняются.

## Раскладка: single-context

Репозиторий монорепозиторный (npm workspaces, `apps/*`), но домен один и общий
для всех приложений, поэтому глоссарий и ADR-и живут в корне:

```
/
├── GLOSSARY.md
├── docs/adr/
│   ├── 0001-....md
│   └── 0002-....md
├── docs/agents/          ← эти файлы: конфигурация скиллов
└── apps/
    ├── api/
    └── web/
```

Если понадобится разделение по контекстам, можно будет перейти на
multi-context: `GLOSSARY-MAP.md` в корне плюс свой `GLOSSARY.md` и
`docs/adr/` внутри каждого контекста.

## Используй словарь глоссария

Когда твой вывод называет доменное понятие (в заголовке задачи, предложении по
рефакторингу, гипотезе, имени теста) — используй термин в том смысле, как он
определён в `GLOSSARY.md`. Не уходи в синонимы, которые глоссарий явно отвергает.

Если нужного понятия в глоссарии ещё нет, это сигнал: либо ты вводишь язык,
которого проект не использует (пересмотри), либо есть реальный пробел (отметь
его для `/domain-modeling`).

## Фиксируй конфликты с ADR

Если твой вывод противоречит существующему ADR, обозначь это явно, а не
переопределяй молча:

> _Противоречит ADR-0007 (event-sourced orders), но есть повод его открыть
> заново, потому что…_
