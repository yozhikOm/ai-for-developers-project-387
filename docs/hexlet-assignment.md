## Описание проекта

«Запись на звонок» это упрощённый сервис бронирования времени по мотивам _Cal.com_.

[Cal.com](https://cal.com/) это сервис, где пользователь публикует доступные интервалы, а другой человек выбирает свободное время и бронирует встречу. У нашего приложения тот же базовый сценарий: владелец публикует доступное время для встреч, а другой пользователь выбирает свободный слот и записывается на звонок.

В проекте нет авторизации, личных кабинетов и интеграций с внешними календарями. Функциональность намеренно ограничена, чтобы сосредоточиться на главном.

В результате должно получиться небольшое, но законченное приложение. Пользователь видит свободные слоты по 15/30 минут, может выбрать время и оформить запись, а владелец календаря смотрит список предстоящих встреч.

Основная функциональность проекта это запись на звонок: типы встреч, календарь свободных слотов, бронирование и список встреч владельца.

## Что должно уметь приложение

В проекте есть две условные роли: владелец календаря и гости. Регистрации и авторизации нет. Владелец календаря это один заранее заданный профиль, который по умолчанию используется в админской части. Гость бронирует слоты без создания аккаунта и без входа в систему.

Владелец календаря может:

- Создавать типы событий. Для каждого типа события задаёт id, название, описание и длительность в минутах.
- Просматривать страницу предстоящих встреч, где в одном списке показаны бронирования всех типов событий.

Гость:

- Может посмотреть страницу с видами брони, где доступно название, описание и длительность.
- Выбирает тип события, открывает календарь и выбирает свободный слот в ближайшие 14 дней.
- Создаёт бронирование на выбранный слот.

Правило занятости:

- На одно и то же время нельзя создать две записи, даже если это разные типы событий.

Окно записи по умолчанию:

- Доступные слоты формируются на 14 дней, начиная с текущей даты.
- Гость может записаться только на свободный слот из этого окна.

## Спецификация и тикеты

Когда решения по карте приняты, соберите их в спецификацию: вызовите `/to-spec`. Этот скилл интервью не проводит, он синтезирует спецификацию из того, что уже обсуждено, поэтому запускать его надо в сессии, где карта и ответы по её задачам загружены в контекст. Спецификация публикуется в трекер и содержит пользовательские истории, принятые решения по реализации и решения по тестированию: на каких границах приложение проверяется.

Дальше разложите спецификацию на тикеты: `/to-tickets`. Тикеты получаются вертикальными: каждый проходит через все слои приложения (контракт, сервер, интерфейс, тесты) и проверяется по отдельности. Каждый тикет объявляет, какие тикеты его блокируют, поэтому всегда видно, что можно брать в работу.

### Требования

- В трекере есть карта решений, задачи карты закрыты с записанными ответами.
- В трекере есть спецификация приложения с пользовательскими историями и решениями по тестированию.
- В трекере есть тикеты с объявленными зависимостями.
- В репозитории есть TypeSpec-контракт, покрывающий сценарии владельца и гостя.
- OpenAPI-спецификация генерируется из TypeSpec, команда генерации описана в репозитории.
- Клиентский SDK для фронтенда генерируется из спецификации.
- Серверные артефакты (типы, проверка запросов, маршруты) генерируются из спецификации, состав зависит от фреймворка.
- Генерация повторяется одной командой, сгенерированное руками не правится.

## Расхождения демо и текста

Это наблюдения, а не часть задания. Их разбирают тикеты карты.

- В демо нет выбора типа события: сразу календарь с фиксированными 30-минутными
  слотами с 09:00 до 18:00. В тексте гость сначала выбирает тип события.
- В демо нет админской части с созданием типов событий.
- Интервал рабочего времени (09:00–18:00) в тексте не задан, в демо есть.
- Поля брони (имя, email) видны только в демо, в тексте не перечислены.
- «Слоты по 15/30 минут» в описании против «длительность в минутах» у типа события:
  связь длительности типа события и шага слотов текстом не определена.
